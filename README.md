# feeda

サーバー負荷を最小にしたRSSリーダー。フィード本文はブラウザのIndexedDBにのみ保存し、サーバー（Flask + Neon）が扱うのは暗号化済みの「購読リスト」と「既読位置」だけです。サーバー側はシードを保存しないため、購読データを復号できません。

構成:

- `backend/` — Flask API（`/api/sync`, `/api/fetch-feed`）。Neon Postgresに暗号化ブロブを保存するだけで、フィード内容は保存・パースしません。
- `public/` — 3ペイン（フィード一覧 / 記事一覧 / プレビュー）のRSSリーダー本体。素のHTML/CSS/JS、ビルド不要。Vercelの静的ファイル配信規約に合わせて`public/`という名前にしています。
- `userscript/` — Tampermonkeyスクリプト。閲覧中のページからRSS/Atomフィードを検出し、未登録のものだけ購読リストに自動追加します。OPMLファイルからの一括インポートにも対応。
- `api/index.py`, `vercel.json` — リポジトリ全体を1つのVercelプロジェクトとしてデプロイするためのエントリポイント（Webアプリの静的配信とFlask APIを同一ドメインで提供）。

## 1. Neonのセットアップ

1. [Neon](https://neon.tech)でプロジェクトを作成し、接続文字列（`postgresql://...`）を控える。Vercelの「Storage」タブからNeon連携を追加した場合は、この手順は不要です（`DATABASE_URL`/`POSTGRES_URL`が自動で設定されます。下記参照）。
2. テーブルは初回のAPIリクエスト時に自動作成されるので、手動でのマイグレーションは不要。

## 2. バックエンド（Flask）をローカルで動かす

リポジトリのルートで実行します（`requirements.txt`はルート直下にあります）。

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp backend/.env.example backend/.env
# backend/.env の NEON_DATABASE_URL を実際の接続文字列に、ALLOWED_ORIGIN をWebアプリのオリジンに書き換える
python backend/app.py
```

`http://localhost:5000/api/healthz` が `{"status": "ok"}` を返せば起動成功です。

## 3. Vercelへのデプロイ（Webアプリ + APIを1プロジェクトで）

このリポジトリは**リポジトリのルートをそのままVercelプロジェクトのRoot Directoryとして**デプロイする構成になっています。WebアプリとFlask APIが同一ドメイン・同一デプロイで公開されます。

- `vercel.json` は明示的な`builds`/`routes`形式（Flask公式ガイドと同じ、いわゆるBuild Output API v1形式）を使っています。`rewrites`（新しいZero-Config向けの書き方）はWSGIアプリへのキャッチオールでは実際のリクエストパスがFlask側に渡らず、全ルートが404になる問題があったため使っていません。
  - `api/index.py`（`backend/`のFlaskアプリをラップしたエントリポイント）が`@vercel/python`でビルドされ、`/api/*`宛のリクエストはすべてそこにルーティングされます（元のパスがそのままFlaskに渡ります）。
  - `public/**`が`@vercel/static`でビルドされ、それ以外のリクエストは静的ファイルとして配信されます。
- `requirements.txt` はルート直下に置いてあります（Vercelのビルドがここから依存関係を検出します）。
- **データベース接続文字列の環境変数名は`NEON_DATABASE_URL`・`DATABASE_URL`・`POSTGRES_URL`のいずれでも構いません**（この順で探します）。VercelのStorageタブからNeon連携を追加した場合は`DATABASE_URL`/`POSTGRES_URL`が自動設定されるので、追加の設定は不要です。手動でNeonプロジェクトを作った場合はEnvironment Variablesに`NEON_DATABASE_URL`を追加してください。
  - **環境変数の追加・変更は既存のデプロイには反映されません。** 保存後、Deployments画面から最新デプロイを選び「Redeploy」するか、`git push`等で新しいデプロイをトリガーしてください。
- `ALLOWED_ORIGIN` は同一ドメイン配信なら省略可（Webアプリからのfetchは同一オリジンになるためCORSは実質不要）。別ドメインからAPIを叩く場合のみそのオリジンを設定してください。
- フィード取得プロキシ（`/api/fetch-feed`）は対象URLをクエリ文字列ではなく `X-Feed-Url` ヘッダーで受け取ります。これはVercelのリライトを経由すると、クエリ文字列中のスラッシュがエンコードされて元のURLと食い違うことがあるための対策です。
- DB接続に必要な環境変数が無い場合でも`/api/healthz`のようなDBを使わないルートは正常に応答します（データベースへの接続はモジュールのimport時ではなく、実際にDBが必要なリクエストが来たときに初めて行う設計になっているため、設定漏れがサイト全体を巻き込んで落とすことはありません）。

## 4. Webアプリを開く

上記のVercelデプロイ後、そのURL（例: `https://your-app.vercel.app`）を開きます。ローカルでWebアプリだけを動かしたい場合は`public/`を`python -m http.server`等で配信してください。

初回起動時にセットアップ画面が表示されます。

- 新規に始める場合は「新しいシードを生成」を押し、表示されたシードを安全な場所に保管してください（**シードを失うと同期データには二度とアクセスできません**）。
- 別端末で既に使っている場合は、そのシードを貼り付けてください。手入力の代わりに、セットアップ画面下部の「QRコードを読み取る」「6桁コードで受け取る」から別端末のシードをそのまま引き継ぐこともできます（後述）。
- 「APIベースURL」は、手順3のように**WebアプリとAPIを同一ドメインでデプロイしている場合は空欄のまま**で構いません（同一オリジンへの相対パスでアクセスします）。ドメインが別の場合のみ、APIのURL（例: `https://your-app.vercel.app`）を入力してください。

### シードの引き継ぎ（QRコード / 6桁コード）

セットアップ済みの端末で画面右上の「シード」→「QRコードで共有」または「6桁コードで共有」を開くと、別端末（またはTampermonkeyスクリプト）にそのままシードを引き継げます。シードの文字列を手でコピー＆ペーストする必要はありません。

- **QRコード**: シードとAPIベースURLをその場でQRコードにエンコードして表示するだけで、サーバーには一切送信されません。別端末のセットアップ画面で「QRコードを読み取る」を開き、カメラで読み取ると設定欄に自動入力されます（内容を確認して「開始」を押してください）。
- **6桁コード**: サーバー上に暗号化した状態で一時的に保管し、6桁の数字コードで受け渡します。コードは数分で失効し、一度受け取ると即座に無効化される使い捨てです（サーバー自体はコードの中身を復号できません）。別端末のセットアップ画面またはTampermonkeyのメニューから「6桁コードで受け取る」を選び、表示されたコードを入力してください。

どちらの画面も、他人に見せると同じ同期データにアクセスされてしまう点はシードそのものと同じです。

feedaはPWA（インストール可能なWebアプリ）にも対応しています。デスクトップ/モバイル問わずブラウザのアドレスバーやメニューから「インストール」するとホーム画面・アプリ一覧にアイコンが追加され、単独のウィンドウで起動できます。`sw.js`はCSS/JS/アイコンなどの静的ファイルを常にネットワークから優先的に取得し（`/api/`宛のリクエスト＝フィード取得・同期は元から対象外で、常にネットワークへ直接アクセスします）、オフライン時や取得に失敗した場合だけキャッシュにフォールバックします。ネットワーク優先にしているのは、キャッシュ優先だとインストール済みの環境にアプリの更新が届かなくなる（＝古いバージョンのまま固定される）ためです。

## 5. Tampermonkeyスクリプトのインストール

1. ブラウザにTampermonkey拡張機能をインストール。
2. `userscript/feeda-autoregister.user.js` の内容をTampermonkeyの新規スクリプトとして貼り付けて保存。
3. シードとAPIベースURLを設定する方法は3通りあります。
   - **自動引き継ぎ**: 同じブラウザで既にWebアプリ（例: `https://feeda-two.vercel.app/`）をセットアップ済みなら、そのページを開くだけで（ページ内に保存済みのシードを検出し）自動的に設定されます。何もする必要はありません。
   - **6桁コード**: Tampermonkeyアイコン →「feeda: 6桁コードでシードを取得」を選び、Webアプリの「シード」→「6桁コードで共有」で表示されたコードを入力します。
   - **手動設定**: Tampermonkeyアイコン →「feeda: シードとAPIを設定」を選び、Webアプリで使っているシードと同じシード、およびAPIベースURLを直接貼り付けます。
4. 以後、RSS/Atomフィードを持つサイトを開くと、そのページに未登録のフィードがあれば自動的に購読リストへ登録されます（初回、ブラウザからAPIドメインへのアクセス許可を尋ねられる場合があります）。

登録済みのフィードには反応しないよう、フィードIDのローカルキャッシュを6時間ごとにサーバーと突き合わせて更新します。

APIベースURLを省略した場合（自動引き継ぎ・6桁コードのいずれでも設定できなかった場合）は、メンテナ自身の本番デプロイ先 `https://feeda-two.vercel.app` がデフォルトとして使われます。自分で別ドメインにデプロイしている場合は、手動設定からそのURLを入力し直してください。

### OPMLの一括インポート

他のRSSリーダーからの乗り換え用に、Tampermonkeyアイコン →「feeda: OPMLをインポート」からOPMLファイルを選択すると、ファイル内の全フィードのうち未登録のものだけをまとめて購読リストに追加できます（登録済みのものは自動的にスキップされます）。

## Webアプリの操作

- フィードの追加・削除はWebアプリ側では行いません。Tampermonkeyスクリプトの自動登録またはOPMLインポートだけがフィードの登録手段です。
- 何もフィードを選択していない状態（起動直後）では、全フィード横断の未読記事一覧が中央ペインに表示されます。フィードごとにブロックにまとまり、各ブロックの先頭にフィード名と「📌」「残す」（一時停止中なら「再開」）ボタンが付きます。フィード名を右クリック（タッチデバイスでは長押し）すると、サイドバーと同じ色パレットでそのフィードに色タグを付けられます（ブロックのヘッダーが左ボーダー＋薄い背景色で示されます）。ブロックの並び順はまずピン留め、次にエンゲージメントスコア（実際に開いた・コメントした・色タグを付けた記事が多いフィードほど上位）、同点なら直近の新着順で決まります（＝満足度優先）。バックグラウンドで新しいフィードが取得できるたびに、そのフィードのブロックはまるごと一覧の一番下に移動します（読んでいる途中のリストの上の方に新着が差し込まれて邪魔をすることはありません）。個別のフィードや「まとめて見る」グループを選んだときも、既読の記事は（「既読も表示」トグルをオンにしない限り）表示されません。3ペイン／マルチカラムでは記事一覧に隣接してプレビューが常に表示されるため、一覧側の各記事はタイトルのみ（時刻・冒頭プレビュー・画像なし）です。検索結果など複数フィードが混ざる一覧だけは、どのフィードの記事か分かるようフィード名を添えます。
- 左のフィード名をクリック（またはマウスホバー）すると、そのフィードの最新記事が自動的にプレビュー表示され、フィード全体が既読になります（個別記事をクリックまたはホバーした場合はその記事の投稿日時まで既読になります）。ホバーでも同様に遷移・既読化するため、一覧上でカーソルを止めるだけで選択が切り替わります。
- キーボードショートカットがあります（画面右上「⋯」→「キーボードショートカット」、または `?` キーでいつでも一覧表示）。矢印キーは左右でフィード一覧・記事一覧・プレビューの間をフォーカス移動、上下でフォーカス中のペインの項目を移動（プレビューではスクロール）。加えて `j`/`k` で次・前の記事、`Enter`/`o` で記事を新しいタブで開く、`m` で選択中のフィード／グループをすべて既読に、`u` ですべての未読へ戻る、`/` で検索欄にフォーカスできます（入力欄にフォーカスがある間は無効になります）。
- ペイン境界をドラッグして幅を調整できます（幅はブラウザに記憶されます）。
- 画面右上の「⋯」ボタンから「NGワード」「シード」「キーボードショートカット」を開けます（利用頻度が低いため常設ボタンから格納しました）。「振り返る」（📖）はよく使うため引き続き常設のアイコンボタンです。「マルチカラム」は振り返る画面では表示されません（読む対象の記事一覧が無いため）。
- 「📊」（マルチカラム、画面幅1920px以上でのみ表示）に切り替えると、記事一覧がタイル状のグリッドではなく、フィード1つにつき1カラムの独立して縦スクロールできる列として横に並びます（横スクロールで他のフィードへ移動）。各カラムの先頭にもフィード名とアクションボタンが付きます。
- カラーパレットによるフィード絞り込み（色タグを付けたフィードがある場合のみ表示）は、検索履歴バーと同じ行の左側に配置されています。
- 検索でヒットした文字列は記事一覧・プレビュー内で黄色背景＋太字にハイライトされます。
- フィード取得中は画面最下部に進捗をプログレスバーで表示します（取得が無い時は表示されません）。
- フィード一覧は頻度グループ内で、日付を持つフィードは最新記事が新しい順、日付を持たないフィードは直近に取得した順に並びます。頻度グループ自体の表示順は「週数回 → 週1回程度 → 月1回程度 → それ以下 → 頻度不明 → 毎日 → 取得しない」で、更新頻度の高い「毎日」グループをあえて下寄りに置くことで、つい毎日更新のフィードばかり見てしまい他が埋もれるのを防いでいます（フィード取得自体の優先順位はこれと別で、頻度が高いフィードから先に取得します）。
- ブラウザのファビコンに、未読記事のあるフィード数（記事数ではない）がバッジ表示されます。
- 画面幅が600px以下（小さめのスマートフォン）になると、3ペインではなく全フィード横断の未読一覧だけのシンプルな1カラムレイアウトに切り替わります。記事は一覧の行がそのままリンクになっており、タップすると元サイトが新しいタブで開きます（アプリ内にプレビューは持ちません）。また、未読の記事を読まずにスクロールで通り過ぎた場合も、その場で既読になります（同期リクエストの連打を避けるため、実際のサーバーへの反映はスクロールが落ち着いてからまとめて行います）。モバイルの未読一覧は、頻度グループの低いフィード（更新が少ないフィード）を優先して上に表示します（グループ内は新着順）。
- デスクトップのフィード名を右クリック（タッチデバイスでは長押し）すると、そのフィードの取得を一時停止／再開できます。一時停止中のフィードは頻度グループの一番下の「取得しない」に移動し、一切フェッチされなくなります（既存の未読記事はそのまま残ります）。この状態は他フィールドと同様に暗号化して同期されます。
- 更新頻度が高い（毎日〜週数回）フィードは、一度も開いた・コメントした・色タグを付けたことがない状態が続くと自動的に一時停止されます（ピン留め・後述の「残す」・手動での一時停止／再開のいずれかが行われているフィードは対象外）。未読一覧の各フィードブロック先頭には「📌」（ピン留め）に加えて、一時停止中なら「再開」ボタン、稼働中なら「残す」ボタンが表示されます。「残す」を押すとそのフィードは以後この自動停止の対象から外れます（＝ノイズは多いがたまに欲しい情報が入るフィード向けのホワイトリスト）。手動での一時停止／再開のボタンはこの一覧からは無くなり、フィード名の右クリック／長押しのみになりました。
- 自動停止されたフィードも、たまに（毎回の巡回でおよそ3割の確率で1件）ランダムに選ばれてその回だけ取得を試みます。一時停止状態自体は変わりませんが、新着があれば未読一覧に反映され、実際に読まれればエンゲージメントスコアが付くため、以後は自動停止の対象から外れます。
- フィード名を中クリックすると、そのフィードのURLをクリップボードにコピーします。
- フィード取得のたびに、記事一覧の内容がほぼ同じフィード同士（記事リンクの一致率80%以上、例えば同じサイトがRSS2版とAtom版を別URLで配信しているケース）を検出し、最初に追加されたもの1件だけを残して残りを自動的に「取得しない」に一時停止します。URLやドメインではなく実際の記事内容で判定するため、はてなブックマークやnoteのように多数のユーザーが同じドメインを共有するプラットフォーム系フィード同士を誤って重複扱いすることはありません。フィード名を右クリック／長押しで一時停止・再開を手動操作したフィードは、以後この自動整理の対象から外れます（他端末の同期にも反映されます）。
- 登録しているフィードの総数は、検索ボックスのプレースホルダー（「N件を検索・URLを貼り付けて登録」）に表示されます。同じ場所にURL貼り付けでの登録方法も添えています。
- 左のフィード一覧の一番上には「📥 すべての未読」ボタンが常に表示されます。フィード選択や検索で記事一覧が別の内容になっていても、これを押せば全フィード横断の未読一覧にいつでも戻れます。
- 画面右上の「⋯」→「シード」から、現在使用中のシードとAPIベースURLをいつでも確認・コピーできます（セットアップ済みの環境ではセットアップ画面が出ないため、別端末やTampermonkeyスクリプトに同じシードを設定したいときはここから参照します）。

## 既読/未読の考え方

個別記事ごとのフラグは持たず、フィードごとに「どの時点までを読んだか」（`readUntil`）だけを1つ管理します。

- 記事の投稿日時が `readUntil` より新しければ未読。
- ただし投稿日時が**システムクロック（現在時刻）より未来**の場合は、`readUntil`に関わらず常に既読として扱います。
- 記事を開くと、その記事の投稿日時まで`readUntil`が自動的に進みます（過去には戻りません）。
- 投稿日時を持たないフィード（date-lessなフィード）は`readUntil`が使えないため、記事一覧のSHA-256フィンガープリント（`contentHash`）を前回見た時点のものと比較し、変化していればフィード全体を未読として扱います。フィードを開くと、その時点のフィンガープリントで追いついた扱いになります。

## フィード取得のスケジューリング

購読数が多くなっても毎回全フィードを巡回しないよう、フィードごとの投稿頻度（毎日・週数回・週1回・月1回・それ以下・頻度不明）に応じて次回チェック時刻（`nextCheckAt`）をクライアント側だけで管理しています（サーバーには送信・保存しません）。ページを開いたときは、この時刻を過ぎているフィードだけを取得します。

頻度の**カテゴリ**（`frequencyGroup`）自体は他のフィールドと同様に暗号化して同期します。`nextCheckAt`と違い、これは「初めて使う端末が、まだ何も取得していない状態でも、頻度の高いフィードから優先して初回スキャンできるようにする」ためのものです。取得対象フィードは`frequencyGroup`の優先順位（毎日→週数回→週1→月1→それ以下→不明）でソートしてから取得します。

- `nextCheckAt`は端末ローカルの値のため、しばらく開いていなかった端末や初めて使う端末では大半のフィードが「取得すべき」判定になります。とある端末で全ての未読を消化した直後に別端末を開いた場合も、既読位置（`readUntil`）自体は同期済みで実際には読む物が無くても、その端末にとっては「まだ一度も取得していない」フィードばかりのため、同様に大量の取得対象が発生します。これを1回の巡回で一気に消化しないよう、1回の巡回（ページを開いたときの自動巡回）で実際に取得するフィード数は上限（30件）を設けており、超過分は次回以降の巡回に持ち越されます。取得自体は最大5件を同時並行で進めるため、直列に1件ずつ取得していた頃より巡回全体の待ち時間は短くなっています。
- 「週1回程度・月1回程度・それ以下・頻度不明」のフィードは、`nextCheckAt`の期限が来ていても曜日を1つに固定し、その曜日以外は巡回対象から除外します（フィードIDから決定的に算出するため設定や同期は不要）。低頻度フィードが積み重なるほど巡回対象が増えていく問題を、頻度に応じたチェック間隔とは別の軸で間引きます。毎日〜週数回更新されるフィードはこれまで通り毎日チェック対象です。

## セキュリティ上のメモ

- `/api/fetch-feed` はSSRF対策として、対象ホストを名前解決した実IPがプライベート/ループバック/リンクローカル等でないか検証してから取得します。
- 記事本文はプレビュー表示前にタグ・属性のアローリストでサニタイズしており、`<script>`等は描画されません。
- シード引き継ぎ用の`/api/pair/<code>`はアカウントIDによる認証を持ちません（そもそもアカウントを持たない端末にシードを渡すための仕組みのため）。6桁コード（100万通り）自体の総当たりを、短い有効期限・一度使うと即失効する使い捨て設計・厳しめのレート制限（`RATE_LIMIT_PAIR_READ`）の3つで防いでいますが、完全に不可能にするものではありません。個人〜小規模利用を前提にした設計判断です。
